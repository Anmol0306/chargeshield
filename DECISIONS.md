# Decisions

What I cut, and why. Five days, one person.
A defensible cut is engineering; an undefended one is scope creep.

| Date | Decision | Reason | Cost accepted |
|---|---|---|---|
| Aug 30 | SQLite over PostgreSQL | Single-process batch analytical workload. Postgres would be resume decoration. | No concurrent writes |
| Aug 30 | Plain HTML over React | ~2h vs ~1 day for the same screen. Metrics don't depend on the UI. | Less polished demo |
| Aug 30 | No agent framework | Workflow is retrieve → classify → propose → validate → gate. A graph library adds indirection, not capability. | — |
| Sep 1 | Exclude 7 high-cardinality ID columns (`card1`, `DeviceInfo`, `card2`, `addr1`, `card5`, `card3`, `addr2`) from the linear baseline | Anonymised codes: numeric magnitude is meaningless to a linear model, and one-hot on `card1` alone is +12,242 columns fit on noise. 46 inputs -> 97 features instead of ~13,000. | Baseline understates achievable performance. Deliberate — it is a floor, and LightGBM splits on these natively |
| Sep 1 | `class_weight="balanced"` on the baseline LR | At 3.5% prevalence an unweighted model at t=0.5 predicts ~nothing positive and reports recall ~0. Makes point metrics non-degenerate. | Destroys calibration. Baseline scores are rankings, not probabilities — calibration is a separate step |
| Sep 1 | Threshold selected on val, applied unchanged to test | Selecting the operating point on test is a second, subtler leak than the split itself. | Test F1 is lower than a test-tuned number would be. That is the point |
| Sep 1 | LightGBM gets the 339 V-columns and all 7 identifiers; the baseline keeps neither | Makes the two models a controlled contrast rather than an algorithm bake-off. The gap measures what the baseline's constraint cost. | Two feature sets to maintain; `ml/metrics.py` shared so scoring is identical |
| Sep 1 | Native LightGBM categoricals via one train-fitted `CategoricalDtype`, not per-split `.astype("category")` | pandas assigns codes per frame in order of appearance; LightGBM stores splits as integer codes. Per-split casting silently scrambles categories at inference. Verified on this data — the mappings genuinely differ. | A learned artifact that must ship with the model |
| Sep 1 | `card1/2/3/5`, `addr1/2` numeric for the tree, not categorical | 12,242 levels overfits LightGBM's categorical splitter; a tree can carve an arbitrary partition of a numeric axis given enough splits. | `DeviceInfo` (string, 1,546 levels) has no numeric fallback and stays categorical |
| Sep 1 | No `scale_pos_weight` on LightGBM | Threshold comes from the val PR curve anyway, so re-weighting buys nothing and damages the probability scale `ml/calibrate.py` needs. The baseline needed `class_weight` only to make t=0.5 non-degenerate. | Point metrics at t=0.5 are degenerate; irrelevant, we don't use t=0.5 |
| Sep 1 | Calibrators fit on `val_fit` (first 70% of val), winner chosen on `val_pick` (last 30%) | Fitting Platt and isotonic on val and then picking by Brier on the same val always picks isotonic — it has more freedom and partly fits val's noise. That is a formality, not a comparison. | val now does three jobs (early stopping, calibrator fit, method selection) and is not a held-out estimate |
| Sep 1 | Selection by Brier, not ECE | Brier is a proper scoring rule, so it rewards being correct *and* honest about uncertainty. ECE alone is gamed by a model that predicts the base rate for everything. | ECE still reported — it is the interpretable number |
| Sep 1 | Kept Platt despite a near-tie | ECE 0.0077 → 0.0050 on test is a real halving of the calibration gap; Brier is a wash (0.02205 → 0.02214). Two parameters, cannot overfit. | Honest framing: calibration was worth *verifying* more than it was worth *applying* |
| Sep 1 | Report calibration restricted to `p >= 0.10`, not just aggregate | 92% of rows score below 0.05, so aggregate ECE measures the region where no decision is made. Aggregate 0.0050 vs decision-region 0.0478 — a 10x difference, and the second one is the real one. | Reported metrics look worse. They are more true |
| Sep 1 | Kept Platt despite +14% over-prediction inside the decision region | Uncalibrated under-predicts total fraud by 19.3% portfolio-wide, which distorts summed expected loss more than a 14% over-count on 5,748 rows. Over-prediction also errs toward ACCEPT — conservative for a defence-only product. | Decision-region miscalibration is a stated limitation of the cost curve, not a hidden one |
| Sep 1 | Dispute-defence cost model, not screening | ChargeShield does not block transactions. Replaced `fp_cost_inr`/`fn_cost_inr` (block-vs-allow) with representment cost + forfeited amount. Polarity inverts: CONTEST at LOW p(fraud). | `config/costs.yaml` scenario keys rewritten |
| Sep 1 | Forfeited-case cost is amount-weighted from `TransactionAmt` | Forfeiting a ₹97,000 dispute is not the same as forfeiting a ₹500 one, and it makes `auto_action_amount_cap_inr` cost-coherent rather than arbitrary. | Requires joining amounts back to the prediction files |
| Sep 1 | `assumed_win_rate_if_legitimate` is an explicit swept parameter | Pricing "forfeited winnable case" is impossible without it, and real chargeback outcomes are not public. Better a stated assumption swept 0.50–0.85 than a silent 1.0. | The most attackable number in the project — labelled as such, never reported as measured |
| Sep 1 | Production bands derived at an assumed 50% dispute-queue fraud rate, not the observed 3.5% | The 3.5% is an artefact of scoring every transaction as a dispute. Tuning the policy engine on a population the analysis itself calls artefactual would be the wrong kind of consistency. | Another stated assumption; full sensitivity reported in `cost_curve.json` |
| Sep 1 | Did NOT tune `human_review_cost_inr` to narrow the review band | The band came out [0.595, 1.000] — wide, and it swallows ACCEPT. Adjusting the input to produce a comfortable output is reverse-engineering, not derivation. | Band width is an open problem for Day 3's policy engine, flagged rather than hidden |
| Sep 1 | Compare against an amount-only static rule, not just defend-none/defend-all | The trivial baselines are easy to beat and flatter the model. The cost-optimal no-model policy is the real adversary, and it already captures most of defend-all's value. | The reported ML contribution drops from ₹93 to ₹84 per dispute. That is the honest number |
| Sep 1 | Rank failure modes by share of unrecovered fraud VALUE, not by recall | A slice with terrible recall on 40 rows is a curiosity, not a failure mode. Value-weighting finds the one that costs money. | — |
| Sep 1 | Added an explicit confound check to the error analysis | Slicing alone reported "identity missing" and "ProductCD W" as two findings; they are one population (Jaccard 0.994). The 2×2 shows W is the driver and identity missingness is not. | Without it the README would have stated a confidently wrong root cause |
| Sep 1 | `tests/test_suite_integrity.py` names the three empty stub files | Docstring-only test files pass silently and inflate the suite count. Declaring them makes the gap visible and forces a deliberate deletion when they are written. | — |
| Sep 2 | Disputes generated from `P(dispute\|fraud)=0.80` / `P(dispute\|legit)=0.03`, not sampled to a target rate | A random sample gives a 3.5% queue, which `cost_curve.py` showed is degenerate. Sampling to hit 50% would be circular — building the population to match the assumption under test. Two named parameters let the composition fall out, and give a reviewer something concrete to argue with. | Queue lands at 48.65%, close to `assumed_dispute_fraud_rate: 0.50` — by construction, and stated as such |
| Sep 2 | Constructed data namespaced under `_chargeshield`, never inside the Razorpay body | The claim is "mirrors Razorpay's documented dispute entity". One invented field sitting next to real ones makes that claim false. `tests/test_disputes.py` asserts the body contains only documented fields. | Slightly noisier JSON |
| Sep 2 | `evidence/requirements.json` rewritten from the actual Razorpay docs | The placeholder used `authentication_record`, `delivery_confirmation`, `service_access_log` — none of which are real Razorpay evidence fields. Real ones are `shipping_proof`, `billing_proof`, `proof_of_service`, `access_activity_log`, etc. Cited with retrieval date. | The reason-code → evidence *mapping* is still constructed, and is labelled as constructed inside the file |
| Sep 2 | Review band derived **per dispute**, not globally | The global band was [0.595, 1.000] — 0.405 wide, and it swallowed ACCEPT entirely. The error was comparing *policy* costs, not *per-dispute* action costs. Per dispute: `1 − (c+h)/(w·A) < p < 1 − (c−h)/(w·A)`, ~0.07 wide at the median. | The band moves with amount, so there is no single number to quote — a table is required |
| Sep 2 | `docs/ARCHITECTURE.md` decision table corrected to match the cost model | It sent `p ≈ 0.47` to HUMAN_REVIEW on "uncertainty". Wrong: at p=0.47 on a ₹6,070 dispute contesting is clearly correct. What warrants a human is proximity to the *cost indifference point* (p*=0.882), not to p=0.5. | The architecture diagram changed to follow the arithmetic, not the reverse |
| Sep 2 | Fabrication checked **before** evidence sufficiency | With sufficiency first, a fabricated citation slips through whenever the real evidence happens to be complete. A proposal that invents evidence is untrustworthy about everything, not just this dispute. | — |
| Sep 2 | Economic-floor rule (`w·A ≤ c` → ACCEPT) placed **before** the evidence gate | A dispute that cannot repay a representment is accepted regardless of score or evidence, so escalating it spends ₹150 of analyst time to learn nothing. | The evidence gate does not fire on futile disputes — deliberate |
| Sep 2 | `decide()` is keyword-only | `p_fraud` and `amount_inr` are both floats; a positional swap would produce a plausible, completely wrong decision that no type checker would catch. | Slightly more verbose call sites |
| Sep 2 | Audit log is JSONL, not SQLite | Append-only, greppable, no migrations, diffable on camera. Each record fingerprints the cost assumptions so it stays explainable after `costs.yaml` changes. | `db_models.py` SQLite remains the Tier-2 path if querying is needed |
| Sep 2 | Price the real gate on the **dispute queue**, not on transactions | The gate needs `reason_code` and evidence; transactions have neither. `ml/evaluate.py` structurally cannot run it, which is why it was silently pricing something else. | Two comparison tables to explain instead of one — but only one of them is the product |
| Sep 2 | Report the −₹18 net **before** the +₹69 actionable-segment figure | The net is the honest headline. Leading with the favourable segment would repeat the exact error of Failure 04 in a subtler form. | The headline number is negative |
| Sep 2 | Human review modelled as a *non-oracle* analyst | Assuming analysts decide perfectly would flatter every comparator except ours (we are the policy that routes to humans), so the optimistic assumption is the conservative one for our claim. | ChargeShield's measured cost is higher than an oracle model would show |
| Sep 2 | `p*(A)` has one implementation, in `app/policy/thresholds.py` | It was implemented twice — the policy engine and the cost analysis could silently disagree about the decision boundary. Same argument that put scoring in `ml/metrics.py`. | `ml/` now imports from `app/policy/`; the policy package stays stdlib-only so this stays cheap |
| Sep 3 | `DisputeProposal` gains a `cited_evidence` field | The original sketch could not support the fabrication check: to know whether a proposal invented a 3-D Secure record you need what it *claimed* to rely on. Without it the "LLM proposes CONTEST → policy BLOCKS" demo is undemonstrable. | One more field for the model to get wrong — which is the point |
| Sep 3 | `p_fraud` is **not** sent to the LLM | The model does language, the classifier does probability, the policy does deciding. Sending the score would let the LLM launder it into a decision and blur the three roles. | The LLM assesses evidence without knowing the fraud risk — deliberate |
| Sep 3 | `llm_service` validates shape, never repairs content | Stripping fabricated citations would mean the gate never fires and no audit record shows the model tried. Content trust belongs to the policy engine. | Fabricated proposals flow through to the gate on purpose |
| Sep 3 | One retry, then template | A provider returning garbage twice is one to stop calling, not to keep paying. | A transient double-failure costs a template response rather than a retry storm |
| Sep 3 | Provider exceptions logged by **type**, not message | Provider error text can carry request context; the type is also what actually distinguishes a timeout from an auth failure. | Less debugging detail in logs — the right trade for credential safety |
| Sep 3 | `/score` accepts partial feature vectors | The model takes 392 features and no caller has them. LightGBM learns a NaN direction per split, so an absent feature is handled exactly as it was in training — where 76% of rows had no identity data. The response reports how many features were supplied, because a prediction from 4 features is not the same evidence as one from 392. | Callers can get a weak prediction without realising — mitigated by reporting the count |
| Sep 3 | Calibrator classes live in `ml/calibrators.py`, never in a `__main__` script | Pickle records the qualified class path; anything defined in an executed script is only loadable by that script. See FAILURES 06. | One more module |
| Sep 3 | No endpoint returns a bare proposal | `/disputes/draft` returns the draft *inside* the decision. An endpoint returning ungated LLM output would let a caller act on it, defeating the design. | `draft` and `analyze` return the same shape |
| Sep 3 | `POST /batch/run` does not write audit records by default | Hitting it during a demo would append 5,013 records per press. | Opt in with `?write_audit=true` |
| Sep 4 | Dashboard calls the live API rather than embedding numbers | Every verdict on screen is a real `POST /disputes/validate`. Hardcoding them would make the demo a slideshow, and the one thing worth showing is that the gate actually runs. | The page needs the server up; there is no static fallback |
| Sep 4 | `GET /metrics` serves the committed evaluation artifacts, not recomputed values | The page is a view of what `make all` produced. If a number on screen disagrees with the repo, the repo is wrong — not the page. | Stale artifacts show stale numbers, which is the correct failure |
| Sep 4 | Dashboard opens on the fabrication scenario | It is the one thing in the project that cannot be inferred from a metrics table. | — |
| Sep 4 | Makefile resolves `$(PYTHON)` rather than calling bare `python`/`uvicorn` | `make api` failed with "uvicorn: No such file or directory" for anyone without the venv activated — including a fresh clone, and `make all` is what a reviewer runs. | — |
| Sep 4 | Evaluation JSON artifacts are committed; `.pkl` and prediction parquets are not | The JSONs are the numbers the README quotes, so a reviewer can check a claim without running anything. The binaries are regenerable and large. | Committed JSONs could go stale against the code — mitigated by the clean-clone reproduction check |
| Sep 4 | The demo asserts its own outcomes and exits non-zero on drift | Recording and testing the same artifact means a policy change that would invalidate the video breaks the build instead of surfacing on playback. | The demo is slightly more code than a print-only script |
| Sep 4 | A test asserts every policy rule has a demo scenario | Without it the demo silently falls behind the engine. It immediately caught two missing rules — including `inside_cost_review_band`, the most interesting one. | Adding a rule now requires adding a scenario |
| Sep 4 | `demo_04` repurposed from `adapter_timeout` to `provider_unreachable` | The Razorpay adapter was cut (Tier 3, never started), so the original case could not be demonstrated. The same property — an external dependency failing must not propagate — is shown against the LLM provider, a dependency that exists in this build and was verified failing against a live 429. | The recorded set no longer includes a Razorpay-specific failure |
| Sep 4 | Keep one OpenAI-compatible client rather than a class per provider | Groq, Google and OpenAI all speak the same wire format, so `LLM_BASE_URL` + `LLM_MODEL` covers all three. A provider hierarchy would add indirection without capability — same argument as not using an agent framework. | Providers that are not OpenAI-compatible would need real work |
